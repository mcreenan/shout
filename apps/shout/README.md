# SHOUT coding workspace

A local browser app that owns chat sessions, runs the existing JOSH/ALLEN VM, asks models for coding judgments, and exposes the execution in a built-in visualization. This extends the owned harness; the original native-adapter prototype remains independently runnable.

## Start

From the repository root:

```sh
npm run setup
npm start
```

Open **http://127.0.0.1:4310**. Requirements: Linux, Node 22+, Bash, Git, `flock`, Rust/Cargo for the initial runtime build, and a browser. Live model mode requires the verified **Codex CLI 0.153.3** with its normal login. Fixture mode needs no model account. `npm start` builds the pinned runtime and installs its runtime dependency if missing.

Use **New session** to select a local workspace path and optionally a test command, such as `npm test` or `python -m pytest`. The test command is supplied by you, not generated by the model. It runs project code with your local user's permissions. The app binds only to loopback and rejects foreign origins; it is not designed for public hosting.

You can override `PORT`, `SHOUT_WORKSPACE` (the default workspace), `SHOUT_STATE_DIR`, `JOSH_BIN`, and `CODEX_BIN`. The defaults store local session history, scenario workspaces and run scratch files under `.runs/shout/`, ignored by Git.

## Use a coding session

Ask for a concrete change, explanation, review, or refactor. The conversation router decides whether to reply, run the coding workflow, or run existing tests. For coding, ALLEN reads a bounded workspace snapshot, requests a typed patch from the model, removes unchanged replacements, and presents the exact proposal for approval.

1. Inspect the **Changes** tab's before/after file contents.
2. Choose **Approve & continue** to apply that exact patch and execute the configured tests, or **Decline changes** to stop this proposal.
3. If tests fail, ALLEN reads fresh files, supplies the observed failure to the model, and permits up to two repair proposals. Every proposal gets a new approval.
4. Follow up in chat. The session retains recent conversation and previous task results.

The model cannot write files or execute commands through its worker. The host invokes only the frozen workspace tools. Before-content checks reject stale edits. A refused or cancelled proposal does not authorize subsequent changes. Already-applied edits remain if a later repair is declined or the task is cancelled; an in-flight filesystem operation can still complete, so cancellation is not rollback.

Enter **`/test`** for deterministic test execution through ALLEN with no model call. Natural-language requests to run tests use one model routing decision and then the same verification workflow. Empty/unconfigured test commands are reported as skipped, never passing.

**Files** browses readable workspace files. **Cancel run** stops pending model/VM work and test process groups. Browser reload reconnects to the current server-side task. Restarting the server restores conversation and traces but marks active tasks interrupted and invalidates their old questions; it does not resume a suspended VM.

## Three guided scenarios

Click a scenario on the welcome screen, choose **Live** or **Fixture**, create the session, and send the prefilled prompt. Each launch creates a fresh isolated project; the templates in this repo remain unchanged.

| Scenario | What to observe | Success condition |
|---|---|---|
| Fix a checkout calculation | Model identifies incorrect discount/tax ordering; one approved file edit | Four checkout tests pass |
| Implement a missing slug utility | Model supplies a missing function using the supplied contract tests | Five slug tests pass |
| Unify inconsistent validation | Model reconciles signup/profile behavior and removes duplicated rules | Five validator tests pass |

To see the starting failure, send `/test` first, then ask “Fix the failures according to the tests.” To exercise a different branch, decline the patch or cancel while approval is pending. Start a fresh scenario session to reset it. Model outputs can differ; use the recorded test results to judge the outcome.

Fixture mode is an offline demonstration of the same real compiler, VM, file operations and tests, with predetermined model answers. Its labels and visualization distinguish scripted judgments from live model calls. Fixture mode supports these scenario solutions, not arbitrary coding intelligence. The repair loop is tested with intentional failures; a live model may solve a scenario on the first attempt.

See [scenario definitions](scenarios/README.md) for exact expected behavior.

## Session VIZ

The right panel provides **Flow**, **Events**, and **Changes** views:

- Flow places recorded events in lanes for you, SHOUT, the model, ALLEN and host tools. Order is chronological. Connectors use shared run/effect IDs, not inferred hidden model reasoning.
- Both the conversation-router calls and ALLEN judgment calls are visible. Fixture sessions label these scripted judgments. A direct `/test` run has zero model calls.
- Select a node or event to see the actual structured input, result, test output, correlation IDs and timestamp. Select `program.loaded` to read the exact ALLEN source used for that run.
- Filter by run or text to inspect a specific execution. Counters describe calls and VM runs, not a measured cost reduction.
- Export downloads the full session JSON, including source snapshots and model prompts. Keep exports with the same care as the workspace code they contain.

## Implementation

```mermaid
sequenceDiagram
  participant User as Browser / user
  participant Session as SHOUT session
  participant Model as Restricted model worker
  participant VM as JOSH / ALLEN
  participant Tools as Workspace tools
  User->>Session: Chat request
  Session->>Model: Typed routing decision
  Model-->>Session: Reply, code, or test
  Session->>VM: Execute typed workflow
  VM->>Session: inspect_workspace
  Session->>Tools: Read bounded files
  Tools-->>VM: Typed snapshot via native host reply
  VM->>Model: Typed patch judgment via host
  Model-->>VM: Summary + exact changes
  VM->>User: Correlated approval via SHOUT
  User-->>VM: Accept or decline via SHOUT
  VM->>Tools: Apply exact approved changes via host
  VM->>Tools: Run user-configured tests via host
  Tools-->>VM: Observed pass/fail + output
  Note over VM,Model: Up to two repairs; each requires fresh approval
  VM-->>Session: Typed outcome
  Session-->>User: Result + live visualization
```

`src/session.mjs` owns conversation, approval binding, persistence and lifecycle. `src/server.mjs` serves the UI and local JSON/SSE interface. `src/workspace.mjs` confines reads and patches and manages test processes. `workflows/coding.allen` owns the coding control flow; `workflows/verify.allen` runs tests directly. The existing owned-harness `Run` supplies actual native JOSH transport and typed provider dispatch with an injected tool catalog. Codex supplies independent judgments through the existing restricted worker.

## Practical limits

This is a functional local coding agent for bounded workspaces, not a complete replacement for Codex or T3. It currently uses one provider adapter, one active task per workspace, and full-file replacements rather than a general shell-agent loop. Hidden files, credential-like paths, symlinks and hardlinks are excluded. Inspectable projects are limited to 200 text files, 64 KiB per file and 512 KiB total; choose a smaller project directory when those limits are exceeded. Large/binary files fail clearly rather than silently producing incomplete context.

An ALLEN coding run allows at most three coding judgments, eight changed files per proposal and ten minutes wall time, including user waits. Tests have a 30-second budget and 128 KiB output cap. Conversation routing is an additional model call. These bounds are not a billed-token cap. Trace history retains the latest 3,000 events and 200 messages per session; start a new session after 50 runs. No external-effect exactly-once guarantee, sandbox against hostile local OS processes, arbitrary multi-agent delegation, provider switching, VM restart recovery, or model-authored ALLEN is claimed.

## Verification

```sh
npm run verify
npm run test:browser
```

The integrated suite passes **58 tests** (26 original + 32 app/engine/workspace tests), plus four original interactive CLI scenarios. Tests execute the real pinned compiler/VM and real file/test tools. Model fixtures provide reproducibility. Coverage includes repairs, declined proposals, stale/hardlinked paths, bounded processes, cancellation and late results, restart invalidation, storage failure, HTTP/SSE and local-origin checks.

The browser test drives the actual UI through scenario creation, chat, diff inspection, approval, edits, tests, VIZ/source inspection, file reading, `/test`, reload, cancellation, and mobile layout. It uses local Chromium or `CHROMIUM_BIN`; otherwise install Playwright's browser with `npx playwright install chromium`.

Separate live verification used real Codex judgments to repair the pricing scenario and passed all four tests. Its approval was explicitly supplied by an automated verification driver in an isolated scenario workspace. Live/browser details are recorded in [GUI verification](../../docs/GUI-VERIFICATION.md).
