# SHOUT coding workspace

A local browser app that owns chat sessions, runs the existing JOSH/ALLEN VM, asks models for coding judgments, and exposes the execution in a built-in visualization. This extends the owned harness; the original native-adapter prototype remains independently runnable.

## Start

From the repository root:

```sh
npm run setup
npm start
```

Open **http://127.0.0.1:4310**. Requirements: Linux, Node 22+, Bash, Git, `flock`, Rust/Cargo for the initial runtime build, and a browser. SHOUT requires the verified **Codex CLI 0.157.1** with its normal login. `npm start` builds the pinned runtime and installs its runtime dependency if missing.

Use **New session** to select a local workspace path and optionally a test command, such as `npm test` or `python -m pytest`. The test command is supplied by you, not generated by the model. It runs project code with your local user's permissions. The app binds to `0.0.0.0` for trusted LAN/Tailscale access, permits this machine's detected addresses and hostnames, and retains same-origin request checks. Network users who can reach it can operate the coding workspace; this is not a public or multi-user hosting configuration.

Startup prints available local, LAN and Tailscale URLs. Permit the selected TCP port in the firewall for the LAN subnet if needed. Tailscale access also follows your tailnet policy. Browser requests use the current origin.

`npm start` loads machine-local settings from the repository's ignored `.env` file. Copy `.env.example` to `.env` and set `SHOUT_ALLOWED_HOSTS=your-hostname.example` to persist a custom DNS alias, then restart. Use `http://your-hostname.example:4310`; DNS must resolve to a reachable address. Explicit process environment variables take precedence over `.env`.

You can override `PORT`, `SHOUT_HOST` (default `0.0.0.0`; use `127.0.0.1` for an explicit local-only launch), `SHOUT_ALLOWED_HOSTS` (comma-separated additional exact hostnames), `SHOUT_WORKSPACE` (the default workspace), `SHOUT_STATE_DIR`, `JOSH_BIN`, and `CODEX_BIN`. The defaults store local session history, scenario workspaces and run scratch files under `.runs/shout/`, ignored by Git.

## Use a coding session

Ask for a concrete change, explanation, review, or refactor. Each session has one persistent model thread, run by `codex app-server`. SHOUT's instructions and the session context (workspace, test command, skills) go in once, when the thread starts. Each later message is sent as typed, and the thread keeps the conversation, including after a restart. The agent replies in text and acts through SHOUT's tools:

- `list_files`, `read_file`, `search_files` and a read-only `git` read the workspace directly.
- `run_skill` runs a skill.
- `run_program` compiles and runs an ALLEN program the agent writes; `allen_guide` loads the authoring guide when it first needs it. A program that doesn't compile goes back to the agent as compiler diagnostics to fix.

Codex's own tools (shell, patching, web search, code mode) are off. The thread uses a SHOUT-owned `CODEX_HOME` under the state directory, so your Codex config, `AGENTS.md`, MCP servers and plugins don't reach it. Only the Codex login is shared, through a symlink to `auth.json`.

`/code` reads the whole workspace when it is small; otherwise one model judgment picks up to 12 relevant files from the listing. It then requests typed snippet edits (an exact `find` text that must occur once, and its replacement), and SHOUT turns them into a full before/after diff for approval.

1. Inspect the **Changes** view's before/after file contents.
2. Choose **Approve & continue** to apply that exact patch and execute the configured tests, or **Decline** to stop this proposal.
3. If tests fail, or an edit's `find` text doesn't match, ALLEN reads fresh files, supplies the observed problem to the model, and permits up to two repair proposals. Every proposal gets a new approval.
4. Follow up in chat. The session retains recent conversation and previous task results.

The model cannot write files or execute commands through its worker. The host invokes only the frozen tool catalog, and the host itself asks for approval before any write or shell command. Before-content checks reject stale edits. A refused or cancelled proposal does not authorize subsequent changes. Already-applied edits remain if a later repair is declined or the task is cancelled; an in-flight filesystem operation can still complete, so cancellation is not rollback.

Enter **`/test`** for deterministic test execution through ALLEN with no model call. A natural-language request to run tests goes to the agent, which usually runs `/test`. Empty/unconfigured test commands are reported as skipped, never passing.

**Files** browses readable workspace files. **Cancel run** stops pending model/VM work and test process groups. Browser reload reconnects to the current server-side task. Restarting the server restores conversation and traces but marks active tasks interrupted and invalidates their old questions; it does not resume a suspended VM.

## Skills

A skill is a repeatable workflow written as one ALLEN file and run as a slash command: `/name arguments`. The VM runs its control flow deterministically. The skill calls host tools (read, search, git, tests, approved edits and shell commands) and asks the model only for typed judgments. Type `/skills` to list skills or `/help` for commands. The conversation router can also pick a skill from its description when a natural-language request matches.

| Command | What it does | Model calls |
|---|---|---|
| `/find <text>` | Literal search, grouped by file | none |
| `/todo` | TODO/FIXME/HACK markers, counted per file | none |
| `/test` | Runs the configured test command | none |
| `/review [focus]` | Reviews the uncommitted diff and new files; findings sorted by severity | 1 |
| `/explain <path or question>` | Explains a file, or picks up to 8 relevant files and answers | 1–2 |
| `/commit [hint]` | Drafts a conventional commit message, lets you confirm or rewrite it, then runs `git commit` after approval | 1 |
| `/code <goal>` | Selects files, proposes snippet edits for approval, runs tests and repairs | several |
| `/new-skill <description>` | Writes a new skill, compile-checks it with up to 3 repairs and saves it after approval | 1–4 |

Skills are discovered in `<workspace>/.shout/skills/`, then `~/.config/shout/skills/`, then the built-ins in [`skills/`](skills/). Earlier scopes hide later ones with the same name. The file name is the command (`[a-z][a-z0-9-]*`, at most 40 characters). The leading `//` comment lines are the header: the first line is the description, and a `// args: <hint>` line gives the argument hint. SHOUT recompiles skills on every use, and `/skills` marks any skill that doesn't compile.

Writes (`workspace.edit`, `workspace.write`) and `shell.run` commands always go through a host approval showing the exact diff or command, whatever the skill does. [`skills/GUIDE.md`](skills/GUIDE.md) is the authoring guide. `/new-skill` gives the same guide, plus the generated tool catalog, to the model. To run a skill from the command line, use `node tools/run-skill.mjs --workspace DIR [--approve] -- "/name args"`.

## Three guided scenarios

Click a scenario on the welcome screen, create the session, and send the prefilled prompt. Each launch creates a fresh isolated project; the templates in this repo remain unchanged.

| Scenario | What to observe | Success condition |
|---|---|---|
| Fix a checkout calculation | Model identifies incorrect discount/tax ordering; one approved file edit | Four checkout tests pass |
| Implement a missing slug utility | Model supplies a missing function using the supplied contract tests | Five slug tests pass |
| Unify inconsistent validation | Model reconciles signup/profile behavior and removes duplicated rules | Five validator tests pass |

To see the starting failure, send `/test` first, then ask “Fix the failures according to the tests.” To exercise a different branch, decline the patch or cancel while approval is pending. Start a fresh scenario session to reset it. Model outputs can differ; use the recorded test results to judge the outcome.

The repair loop is tested with intentional failures; a live model may solve a scenario on the first attempt.

See [scenario definitions](scenarios/README.md) for exact expected behavior.

## Tabs, files and inspector

The session chat is a tab. SHOUT's replies render Markdown: headings, lists and task lists, quotes, tables, highlighted code blocks, inline code, emphasis and links. The renderer builds DOM nodes directly, so model output can't inject HTML. A link to a workspace path such as `[pricing](src/pricing.mjs#L12)` opens that file beside the chat. Your own messages and tool output stay plain text.

Files and visualizations open as further tabs, and you can arrange them in splits:

- Use the split buttons in a tab strip to put the active tab beside or below its group. You can also drag a tab, a file, or a view launcher onto a tab strip to move it, or onto the edge of a pane to split. Drag the dividers to resize. Middle-click or × closes a tab. The chat tab can move, but it can't be closed. Each session's layout is saved in the browser.
- **Files** (right panel) shows the workspace tree. Click a file to open a syntax-highlighted, read-only tab. Use the split icon to open it to the side. Open file tabs reload when a run finishes.
- **Inspector** (right panel) is a summary: view launchers, an activity overview of recent events by lane, runs, changed files and recent events. Each item opens the richer **Flow**, **Events** or **Changes** view as a tab, or to the side or below. **View changes** on an approval opens Changes beside the chat so the approval stays visible.

**ALLEN programs** have their own **Program** tab:

- Each workflow run gets a card in the chat. The card shows the workflow file, run state and the effects it performed in order (tool calls, model judgments, approvals). **View program** opens the executed source beside the chat.
- The Program tab shows syntax-highlighted ALLEN source. Every line that performs an effect is marked and annotated with what happened there in that run, such as `1× call`, `2× judgments`, `not reached`, or `waiting for you` while the VM is suspended on it. Click an annotation to see those events.
- The source selector follows the latest run by default. It can also pin a specific run or show the built-in `code.allen` / `test.allen` before anything has run. The Inspector lists **Program** first among its views, and each run row has a program button.

In the Flow, Events and Changes views:

- Flow places recorded events in lanes for you, SHOUT, the model, ALLEN and host tools. Order is chronological. Connectors use shared run/effect IDs, not inferred hidden model reasoning.
- The agent's steps (its thinking between tool calls) and ALLEN judgment calls are both visible. A direct `/test` run has zero model calls.
- Select a node or event to see the actual structured input, result, test output, correlation IDs and timestamp. Selecting `program.loaded` offers a shortcut to that run's Program tab.
- Each view tab has its own run and text filters, so two Flow tabs can show different runs side by side.
- Changes shows syntax-highlighted before/after diffs with old and new line numbers.
- Export downloads the full session JSON, including source snapshots and model prompts. Keep exports with the same care as the workspace code they contain.

## Implementation

```mermaid
sequenceDiagram
  participant User as Browser / user
  participant Session as SHOUT session
  participant Agent as Agent thread (codex app-server)
  participant Model as Restricted model worker
  participant VM as JOSH / ALLEN
  participant Tools as Workspace tools
  User->>Session: Chat request
  Session->>Agent: The message (instructions were sent once, at thread start)
  Agent->>Session: Tool call: run_skill code (or read tools, run_program)
  Session->>VM: Execute typed workflow
  VM->>Session: workspace.inspect (or list + model file choice + read_many)
  Session->>Tools: Read bounded files
  Tools-->>VM: Typed files via native host reply
  VM->>Model: Typed edit judgment via host
  Model-->>VM: Summary + exact snippet edits
  VM->>Session: workspace.edit
  Session->>User: Exact diff for approval
  User-->>Session: Accept or decline
  Session->>Tools: Apply exact approved changes
  VM->>Tools: Run user-configured tests via host
  Tools-->>VM: Observed pass/fail + output
  Note over VM,Model: Up to two repairs; each requires fresh approval
  VM-->>Session: Typed outcome
  Session-->>Agent: Tool result
  Agent-->>Session: Reply
  Session-->>User: Result, reply + live visualization
```

`src/session.mjs` owns conversation, command routing, the agent's tools, host approvals, persistence and lifecycle. `src/agent.mjs` is the `codex app-server` client: one process, one thread per session, SHOUT's dynamic tools. `src/skills.mjs` discovers and compile-checks skills. `src/tools.mjs` is the host tool catalog and its handlers. `src/server.mjs` serves the UI and local JSON/SSE interface. `src/workspace.mjs` confines reads, searches and edits and manages command processes. `skills/code.allen` owns the coding control flow and `skills/test.allen` runs tests directly. Skill checking uses `shout-allen-check` (`tools/allen-check/`), built by `tools/setup-josh.sh` from the same pinned compiler crates, because `allen check` has no tool catalog and JOSH load errors carry no diagnostics. The existing owned-harness `Run` supplies actual native JOSH transport and typed provider dispatch with an injected tool catalog. Codex supplies program judgments (`model.request`) through the existing restricted worker, one stateless call each.

## Practical limits

This is a functional local coding agent for bounded workspaces, not a complete replacement for Codex or T3. It currently uses one provider adapter and one active task per workspace, and shell commands only run through approved `shell.run` calls rather than a general shell-agent loop. Hidden files (except `.shout/`), credential-like paths, symlinks and hardlinks are excluded. Files are limited to 256 KiB each. A whole-workspace snapshot is limited to 200 text files and 512 KiB total; beyond that, `/code` selects files instead. Large/binary files fail clearly rather than silently producing incomplete context.

A skill run allows at most 16 model judgments, 128 tool calls and ten minutes wall time, including user waits; `/code` makes at most three edit proposals. Tests have a 30-second budget and 128 KiB output cap. Agent turns are additional model calls, with at most 60 tool calls per message. These bounds are not a billed-token cap. Trace history retains the latest 3,000 events and 200 messages per session; start a new session after 50 runs. No external-effect exactly-once guarantee, sandbox against hostile local OS processes, arbitrary multi-agent delegation, provider switching, or VM restart recovery is claimed. `/new-skill` writes ALLEN with a model, but only compiled source is offered, and saving it needs approval.

## Verification

```sh
npm run verify
npm run test:browser
```

The integrated suite passes **97 tests** (28 original prototype tests + 69 app/engine/workspace/network/layout/flow/markdown/skills tests), plus four original interactive CLI scenarios. Tests execute the real pinned compiler/VM and real file/test tools. A scripted agent and scripted judgments (`test/doubles.mjs`) provide reproducibility. Coverage includes repairs, declined proposals, stale/hardlinked paths, bounded processes, cancellation and late results, restart invalidation, storage failure, HTTP/SSE and local-origin checks.

The browser test drives the actual UI through scenario creation, chat, diff inspection, approval, edits, tests, inspector/source inspection, file reading, `/test`, reload, cancellation, and mobile layout. It uses local Chromium or `CHROMIUM_BIN`; otherwise install Playwright's browser with `npx playwright install chromium`.

Separate live verification used real Codex judgments to repair the pricing scenario and passed all four tests. Its approval was explicitly supplied by an automated verification driver in an isolated scenario workspace. Live/browser details are recorded in [GUI verification](../../docs/GUI-VERIFICATION.md).
