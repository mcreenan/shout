# JOSH/ALLEN implementation audit for an owning agent runtime

Research date: 2026-09-23. Source: [mcreenan/josh-allen at abb8a9782fc438d1b87e8aa2fdaea65e5db633c3](https://github.com/mcreenan/josh-allen/tree/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3). This audit examines source, tests, and project specifications. References are pinned to that commit rather than the older installed plugin. “Implemented” below means present in inspected code; test execution is reported separately.

## Finding

The strongest version of the idea is an **owning host around substantial existing language/runtime infrastructure**, followed by explicitly designed durability. The repository already has a VM, typed effects, cooperative scheduling, provider abstractions, and deterministic execution replay. Its packaged MCP adapter is a prompt-mediated compatibility layer, and that layer cannot give the model the same control as an owning harness. This does **not** establish that JOSH/ALLEN is nonviable, or that all integration into existing harnesses is impossible.

The repository itself reaches a similar conclusion: PD-11 accepts native host routing and says manual `next_action` forwarding is a compatibility/diagnostic mode. An open harness adapter implementing PD-11 phases 2–3 is a credible, smaller experiment alongside the proposed owning harness. Durable checkpoint/resume remains explicitly unimplemented. [PD-11 native routing](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/roadmap/proposals/PD-11.md#L154-L191), [roadmap durability status](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/ROADMAP.md#L99-L114).

## What the present bridge actually does

1. An MCP call starts a JOSH child process, generates a bridge session token and execution ID, and initializes an attached JOSH connection with `invoking_session_id: mcp-<token>`.
2. It supplies a frozen host projection, tool catalog, and explicit execution grants.
3. When JOSH emits an allowed provider request, Python stores **one pending action**, returns `state: waiting`, and includes a suggested `resume_arguments_shape`.
4. The invoking model must interpret that action, perform the host-native operation, copy the structured result, and call `allen_session_resume`.
5. Resume checks the token/request ID, forwards the reply, and advances until another provider request or terminal result.

These are implemented control transitions, not merely usage conventions. [Session and next-action representation](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L452-L503), [advance loop](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L627-L667), [start](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L698-L769), [resume](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L788-L824).

The awkwardness follows from ownership. JOSH can identify a typed effect and validate its reply, but this adapter cannot directly schedule the parent harness’s model turn, inspect its complete registry, or dispatch its native agent operations. Instead, operational plumbing reenters the model’s prompt as instructions. Every such crossing adds a model-mediated routing opportunity and makes structured host behavior depend on compliance with instructions. That is an architectural inference from the control flow; this audit does not quantify its real-world failure rate.

Important qualifications:

- **Catalog completeness is scoped to the producer.** The default bridge catalog really contains only `allen_integration_echo`; it is not an enumeration of all Codex/Claude/MCP tools. A host-owned injection file can replace the catalog and grants, but injection alone does not implement native dispatch. [Default catalog](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L224-L264), [projection injection](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L538-L556).
- **An ID is not proof of the invoking host session.** The adapter generates an identity label and declares `prompt_assisted`; the specification explicitly distinguishes this from authenticated binding. [Default binding](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L295-L300), [binding semantics](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/docs/implementation-spec.md#L462-L467).
- **Waiting is currently a live-process condition.** The bridge keeps sessions in a Python dictionary and communicates with retained child-process pipes. Resume requires an existing session and pending request. Its wall-time ceiling is one hour; waiting does not imply persistence across a process restart. [Session storage](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L516-L545), [deadline](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L689-L691), [session lookup](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L777-L796).
- **The bridge exposes one action at a time; the VM itself is more capable.** Do not mistake the bridge’s single pending slot for absence of VM concurrency. The VM has multiple tasks and pending effects, discussed below.
- **Some facilities are deliberately unavailable through this adapter.** Its advance loop rejects unsupported providers, explicitly including transcript and permission requests; execution grants include no filesystem/network/subprocess authority. [Provider allowlist handling](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L642-L658), [execution grants](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/plugins/josh-allen/mcp/server.py#L748-L765).

## Durability and execution-control gaps

**The public execution API runs to a terminal outcome.** Internal task state is constructed locally inside execution; `CheckpointObserver` explicitly cannot suspend execution or create tasks. A “checkpoint” in this API is a before-instruction observation, not a recovery checkpoint. An owning runtime needs a new stepping/suspension interface or a durable replay driver; reusing the name alone does not supply either. [Checkpoint contract](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/allen-vm/src/lib.rs#L1025-L1044), [local machine construction](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/allen-vm/src/lib.rs#L1888-L1915).

**The current replay journal is not restart recovery.** Its recorder holds pending/completed entries in memory; it finalizes a bounded replay document. `ReplaySession` accepts no live provider, and its finish check demands all entries/completions consumed and the recorded terminal outcome matched. There is no inspected “replay a committed prefix, then safely switch to live execution” mode. Adding one requires durable writes, effect intent/outcome boundaries, unknown-outcome handling, idempotency/reconciliation, and scheduler/version rules. [Recorder state and finalization](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/allen-testkit/src/lib.rs#L607-L614), [finalization constraints](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/allen-testkit/src/lib.rs#L750-L788), [replay construction](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/allen-testkit/src/lib.rs#L796-L831), [exhaustion and outcome](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/allen-testkit/src/lib.rs#L951-L990).

**Opaque runtime resources complicate persistence.** The testkit explicitly does not serialize VM capability, future, task, closure, workspace, or subagent values. A durable VM needs a persistent data representation and stable references for resources, with authority reacquisition/revalidation rather than restoring live pointers or assuming old grants remain valid. This is new design work, not proof that existing VM state cannot be adapted. [Testkit scope](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/allen-testkit/src/lib.rs#L1-L6).

**Connection/session state is execution-local.** `josh-host` creates session and pending registries in memory for each connection; a session permits one active execution at a time. This is compatible with a process-per-run worker model, but a multi-session supervisor, persistent inbox/outbox, durable timers, reconnect semantics, and restart ownership must sit above it or change the contract. [Connection creation](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/josh-host/src/server.rs#L52-L76), [pending registry](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/josh-host/src/server.rs#L908-L937), [single execution preflight](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/josh-host/src/session.rs#L531-L548).

**Projection is only phase one.** Non-tool sections currently carry manifests/counts, not typed contextual items usable by ALLEN. The projection digest is not yet bound into accepted events, artifacts, or replay. Transcript/resource identity, context visibility, and durable authorization history need additional contracts. [Projection scope](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/docs/implementation-spec.md#L439-L479).

**Same-agent callbacks need an explicit turn protocol.** `InvokingAgentProvider` intentionally binds one invoking agent and cannot select another session/model. In an owning harness, `agent.ask` therefore cannot casually mean “start an unrelated model call.” It needs a defined parent-session continuation/context and scheduler rule, especially when the parent model has an outstanding tool call awaiting the VM. Whether a given model API permits the intended transcript arrangement is a provider-specific integration test. [Invoking-agent binding](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/allen-runtime/src/lib.rs#L787-L829).

## What the newer Executor integration changes

The inspected HEAD includes `josh run --executor`. It validates exact grants against a frozen catalog, requires object-root tool inputs and a fixed error schema, and invokes `executor call <name> @<private-input-file>` through the process broker. This closes a real unattended **tool dispatch** gap. It is not native parent-agent/session orchestration: the runner routes only `tool/invoke` through this adapter and returns unavailable responses for other unsupported methods. [Executor preflight](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/josh/src/executor_provider.rs#L42-L110), [runner dispatch](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/josh/src/runner.rs#L508-L546), [adapter scope and no-retry contract](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/docs/implementation-spec.md#L527-L574).

The fake-Executor integration tests assert exact argv, private input permissions, cleanup, and no shell expansion. Other tests cover malformed output, timeouts, executable replacement, and no retries. They demonstrate local boundary testing, not validation against a real remote production service. [Success/security test](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/josh/tests/runner_tool_provider.rs#L162-L209), [timeout and replacement tests](https://github.com/mcreenan/josh-allen/blob/abb8a9782fc438d1b87e8aa2fdaea65e5db633c3/crates/josh/tests/runner_tool_provider.rs#L309-L455).

## Smallest useful integration experiments

These are proposals inferred from the existing seams, not implemented features.

**Experiment A: native host adapter without changing ALLEN.** Use an open host or a small custom host to speak the current JOSH protocol. Freeze its registry; route tool/model/user/subagent requests directly; keep a request map and cancellation ownership in ordinary code. Run a script that requests model judgment, invokes a deterministic tool, asks a human, and returns to the same chat. Judge success by zero model-written routing/resume envelopes and reliable cancellation. This implements the intent of PD-11 phases 2–3 and tests whether the main pain can be removed without a new harness product.

**Experiment B: owning supervisor embedding the Rust runtime.** Use `RuntimeProviders` with channel-backed providers and call `prepare_launch` / `execute_prepared_with_context` on a VM worker thread. Let a supervisor own session state, model API turns, tool dispatch, user messages, and child tasks. This permits one product runtime while retaining a process/thread isolation boundary. Avoid exposing borrowed Rust provider state as the durable data model; durable effect requests/results should be separate serializable records.

**Experiment C: durable execution semantics.** Only after A or B proves the experience, add a durable effect ledger and a narrow recovery mode. Crash immediately before dispatch, after remote success but before local commit, while awaiting a user, and while two effects finish out of order. A plain read-only retry success is insufficient evidence for safe mutation recovery. Existing replay tests should remain strict regression tests; recovery should have separately specified live-tail semantics.

A new language is not required to run A or B. If their main limitation becomes the authoring experience, context/turn semantics, or durable data restrictions, that supplies evidence for an ALLEN evolution rather than a speculative rewrite.

## Verification and limits

Executed locally:

```text
PYTHONDONTWRITEBYTECODE=1 python -m unittest test_server.FramingTests test_server.BridgeValidationTests
Ran 18 tests in 0.016s — OK
```

These tests cover framing, bounded sessions, resume matching, cancellation/late resume, expiry, failure propagation, projection validation, and prompt-governed child defaults. No paid model calls, real external tool mutations, or Rust build were performed. Rust integration tests and end-to-end Python tests were inspected rather than executed.

The audit establishes concrete adapter/runtime behavior and explicit missing durability. It does not establish measured reliability in Codex/Claude, model authoring accuracy, throughput, recovery performance, or the economics of a new harness. Those require the experiments above. The claim “we must own the harness” is therefore a promising product hypothesis, not a theorem forced by the current bridge.
