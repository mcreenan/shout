JOSH/ALLEN implementation audit for an owning agent runtime

Research date: 2026-09-23. Source: mcreenan/josh-allen at abb8a9782fc438d1b87e8aa2fdaea65e5db633c3. This audit examines source, tests, and project specifications. References are pinned to that commit rather than the older installed plugin. “Implemented” below means present in inspected code; test execution is reported separately.

Finding

The strongest version of the idea is an owning host around substantial existing language/runtime infrastructure, followed by explicitly designed durability. The repository already has a VM, typed effects, cooperative scheduling, provider abstractions, and deterministic execution replay. Its packaged MCP adapter is a prompt-mediated compatibility layer, and that layer cannot give the model the same control as an owning harness. This does not establish that JOSH/ALLEN is nonviable, or that all integration into existing harnesses is impossible.

The repository itself reaches a similar conclusion: PD-11 accepts native host routing and says manual next_action forwarding is a compatibility/diagnostic mode. An open harness adapter implementing PD-11 phases 2–3 is a credible, smaller experiment alongside the proposed owning harness. Durable checkpoint/resume remains explicitly unimplemented. PD-11 native routing, roadmap durability status.

What the present bridge actually does

  1. An MCP call starts a JOSH child process, generates a bridge session token and execution ID, and initializes an attached JOSH connection with invoking_session_id: mcp-<token>.
  2. It supplies a frozen host projection, tool catalog, and explicit execution grants.
  3. When JOSH emits an allowed provider request, Python stores one pending action, returns state: waiting, and includes a suggested resume_arguments_shape.
  4. The invoking model must interpret that action, perform the host-native operation, copy the structured result, and call allen_session_resume.
  5. Resume checks the token/request ID, forwards the reply, and advances until another provider request or terminal result.

These are implemented control transitions, not merely usage conventions. Session and next-action representation, advance loop, start, resume.

The awkwardness follows from ownership. JOSH can identify a typed effect and validate its reply, but this adapter cannot directly schedule the parent harness’s model turn, inspect its complete registry, or dispatch its native agent operations. Instead, operational plumbing reenters the model’s prompt as instructions. Every such crossing adds a model-mediated routing opportunity and makes structured host behavior depend on compliance with instructions. That is an architectural inference from the control flow; this audit does not quantify its real-world failure rate.

Important qualifications:

  • Catalog completeness is scoped to the producer. The default bridge catalog really contains only allen_integration_echo; it is not an enumeration of all Codex/Claude/MCP tools. A host-owned injection file can replace the catalog and grants, but injection alone does not implement native dispatch. Default catalog, projection injection.
  • An ID is not proof of the invoking host session. The adapter generates an identity label and declares prompt_assisted; the specification explicitly distinguishes this from authenticated binding. Default binding, binding semantics.
  • Waiting is currently a live-process condition. The bridge keeps sessions in a Python dictionary and communicates with retained child-process pipes. Resume requires an existing session and pending request. Its wall-time ceiling is one hour; waiting does not imply persistence across a process restart. Session storage, deadline, session lookup.
  • The bridge exposes one action at a time; the VM itself is more capable. Do not mistake the bridge’s single pending slot for absence of VM concurrency. The VM has multiple tasks and pending effects, discussed below.
  • Some facilities are deliberately unavailable through this adapter. Its advance loop rejects unsupported providers, explicitly including transcript and permission requests; execution grants include no filesystem/network/subprocess authority. Provider allowlist handling, execution grants.

Implemented foundations worth retaining

Foundation Evidence and reuse implication
Explicit VM execution state MachineFrame contains registers, program counter, scope state, and a continuation slot. MachineTask owns frames and a Ready / Waiting / Completed state; waits distinguish effect, task, scope, and return. This is a useful basis for a resumable interpreter, though it is not a serialized continuation format. Frames, tasks and waits.
Cooperative scheduler and asynchronous effects TaskMachine tracks tasks/effect IDs/event IDs and rotates through ready tasks. Pending effects are polled. A new host can reuse effect-driven execution rather than inventing coroutine semantics from scratch. Machine, ready selection, effect polling.
Host-neutral provider seam RuntimeProviders has tool, invoking-agent, model, user, child-agent, external-grant, and HTTP providers. This already separates deterministic execution from host-owned intelligence and interaction. Provider bundle.
Preflight separate from execution prepare_launch produces a one-shot value fixing artifact, validated input, authority, catalog, and budgets; execute_prepared_with_context takes providers, cancellation, and observer. Preserve that invariant in any new supervisor. Preflight, execution seam.
Exact requirements instead of textual guesses Program loading derives required tools from the verified artifact; bridge startup checks those requirements against host-authorized names. A real host can use these requirements for permission UI and dispatch. Load result, grant check.
Protocol lifecycle and cancellation JOSH already routes provider requests over a framed protocol with scoped IDs and ordered events. Native routing need not use the Python prompt bridge. Protocol contract.
Deterministic effect replay The testkit binds artifact/runtime/contract/policy/catalog/capability identities, records completion order, validates requests/results, and requires exact final-channel agreement. Useful for regression testing and as design input for future recovery semantics. Replay contract.
Task and budget observations Existing observer events describe task lifecycle, provenance, and budget warnings. These are a starting point for an activity UI. They are not a durable event log. Observer API.

Durability and execution-control gaps

The public execution API runs to a terminal outcome. Internal task state is constructed locally inside execution; CheckpointObserver explicitly cannot suspend execution or create tasks. A “checkpoint” in this API is a before-instruction observation, not a recovery checkpoint. An owning runtime needs a new stepping/suspension interface or a durable replay driver; reusing the name alone does not supply either. Checkpoint contract, local machine construction.

The current replay journal is not restart recovery. Its recorder holds pending/completed entries in memory; it finalizes a bounded replay document. ReplaySession accepts no live provider, and its finish check demands all entries/completions consumed and the recorded terminal outcome matched. There is no inspected “replay a committed prefix, then safely switch to live execution” mode. Adding one requires durable writes, effect intent/outcome boundaries, unknown-outcome handling, idempotency/reconciliation, and scheduler/version rules. Recorder state and finalization, finalization constraints, replay construction, exhaustion and outcome.

Opaque runtime resources complicate persistence. The testkit explicitly does not serialize VM capability, future, task, closure, workspace, or subagent values. A durable VM needs a persistent data representation and stable references for resources, with authority reacquisition/revalidation rather than restoring live pointers or assuming old grants remain valid. This is new design work, not proof that existing VM state cannot be adapted. Testkit scope.

Connection/session state is execution-local. josh-host creates session and pending registries in memory for each connection; a session permits one active execution at a time. This is compatible with a process-per-run worker model, but a multi-session supervisor, persistent inbox/outbox, durable timers, reconnect semantics, and restart ownership must sit above it or change the contract. Connection creation, pending registry, single execution preflight.

Projection is only phase one. Non-tool sections currently carry manifests/counts, not typed contextual items usable by ALLEN. The projection digest is not yet bound into accepted events, artifacts, or replay. Transcript/resource identity, context visibility, and durable authorization history need additional contracts. Projection scope.

Same-agent callbacks need an explicit turn protocol. InvokingAgentProvider intentionally binds one invoking agent and cannot select another session/model. In an owning harness, agent.ask therefore cannot casually mean “start an unrelated model call.” It needs a defined parent-session continuation/context and scheduler rule, especially when the parent model has an outstanding tool call awaiting the VM. Whether a given model API permits the intended transcript arrangement is a provider-specific integration test. Invoking-agent binding.

What the newer Executor integration changes

The inspected HEAD includes josh run --executor. It validates exact grants against a frozen catalog, requires object-root tool inputs and a fixed error schema, and invokes executor call <name> @<private-input-file> through the process broker. This closes a real unattended tool dispatch gap. It is not native parent-agent/session orchestration: the runner routes only tool/invoke through this adapter and returns unavailable responses for other unsupported methods. Executor preflight, runner dispatch, adapter scope and no-retry contract.

The fake-Executor integration tests assert exact argv, private input permissions, cleanup, and no shell expansion. Other tests cover malformed output, timeouts, executable replacement, and no retries. They demonstrate local boundary testing, not validation against a real remote production service. Success/security test, timeout and replacement tests.

Smallest useful integration experiments

These are proposals inferred from the existing seams, not implemented features.

Experiment A: native host adapter without changing ALLEN. Use an open host or a small custom host to speak the current JOSH protocol. Freeze its registry; route tool/model/user/subagent requests directly; keep a request map and cancellation ownership in ordinary code. Run a script that requests model judgment, invokes a deterministic tool, asks a human, and returns to the same chat. Judge success by zero model-written routing/resume envelopes and reliable cancellation. This implements the intent of PD-11 phases 2–3 and tests whether the main pain can be removed without a new harness product.

Experiment B: owning supervisor embedding the Rust runtime. Use RuntimeProviders with channel-backed providers and call prepare_launch / execute_prepared_with_context on a VM worker thread. Let a supervisor own session state, model API turns, tool dispatch, user messages, and child tasks. This permits one product runtime while retaining a process/thread isolation boundary. Avoid exposing borrowed Rust provider state as the durable data model; durable effect requests/results should be separate serializable records.

Experiment C: durable execution semantics. Only after A or B proves the experience, add a durable effect ledger and a narrow recovery mode. Crash immediately before dispatch, after remote success but before local commit, while awaiting a user, and while two effects finish out of order. A plain read-only retry success is insufficient evidence for safe mutation recovery. Existing replay tests should remain strict regression tests; recovery should have separately specified live-tail semantics.

A new language is not required to run A or B. If their main limitation becomes the authoring experience, context/turn semantics, or durable data restrictions, that supplies evidence for an ALLEN evolution rather than a speculative rewrite.

Verification and limits

Executed locally:

PYTHONDONTWRITEBYTECODE=1 python -m unittest test_server.FramingTests test_server.BridgeValidationTests
Ran 18 tests in 0.016s — OK

These tests cover framing, bounded sessions, resume matching, cancellation/late resume, expiry, failure propagation, projection validation, and prompt-governed child defaults. No paid model calls, real external tool mutations, or Rust build were performed. Rust integration tests and end-to-end Python tests were inspected rather than executed.

The audit establishes concrete adapter/runtime behavior and explicit missing durability. It does not establish measured reliability in Codex/Claude, model authoring accuracy, throughput, recovery performance, or the economics of a new harness. Those require the experiments above. The claim “we must own the harness” is therefore a promising product hypothesis, not a theorem forced by the current bridge.
